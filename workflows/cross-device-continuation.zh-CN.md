# 跨设备接续工作流

> 语义源：英文 [Cross-Device Continuation Workflow](cross-device-continuation.md)。本文档为中文对应版本。

## 目的

当对话、产品仓库的未提交变更和本地环境状态无法自动共享时，安全地在另一台设备上恢复工作。

使用单独的私有开发状态仓库传递简洁的任务状态；仅在需要时传递短期 patch。它是可同步的工作记忆，而不是第二个产品仓库。

## 边界

- 产品仓库仍是产品代码、架构、决策、测试、发布和已提交历史的事实来源。
- 开发状态仓库存放当前任务状态、对产品事实的引用和临时 patch 传输产物。
- 不要复制完整对话。只记录安全恢复所需的决策、证据、未解决问题和下一步行动。
- Patch 是临时传输物，不是替代历史。它必须绑定精确的产品仓库基础提交，并在集成或放弃后退役。
- 不要在任务状态或 patch 中存储凭据、令牌、私钥或其他机密。

## 建议的开发状态仓库结构

```text
<development-state-repository>/
├── README.md
├── projects/
│   ├── registry.md
│   └── <project-id>/
│       ├── project.md
│       ├── active/<task-id>/
│       │   ├── handoff.md
│       │   └── patches/
│       │       ├── manifest.md
│       │       └── 001-<base-short-sha>.patch
│       └── archive/
├── global/current-focus.md
└── devices/<device-id>.md
```

`projects/registry.md` 是导航索引。每个 `project.md` 记录稳定接续配置，例如产品仓库定位符、默认分支、入口文档和验证引用。每个活动任务恰有一个 `handoff.md`；不要将实时状态拆分到状态、下一任务和决策文件中。`global/current-focus.md` 只是便捷指针，并链接到权威任务交接记录。

## 工作流

### 1. 在源设备准备交接

检查产品仓库的分支、完整 `HEAD` 提交、工作树状态、相关 diff 和验证结果。使用[开发交接模板](../templates/development-handoff-template.md)创建或更新 `handoff.md`。将观察事实与推论和建议的下一步行动分开记录。

若必须迁移未提交变更，创建 patch 及其[Patch 清单](../templates/patch-manifest-template.md)。精确说明 patch 包含和排除的内容，包括未跟踪、已忽略、生成或二进制文件。除非已验证，否则不要声称它代表整个工作树。

### 2. 发布可恢复状态

依照自身访问控制提交并同步开发状态仓库。实际可行时，在同一状态仓库修订中保留交接记录及必要的 patch 产物。不要向状态仓库提交产品代码或产品本地机密。

### 3. 验证目标设备

同步开发状态仓库并读取选定的 `project.md`、`handoff.md` 和 patch 清单。同步产品仓库并检查其远程、分支、`HEAD`、工作树和引用文件。

将交接记录视为待验证的声明，而不是仓库证据的替代品。若产品仓库与 patch 基础不匹配、包含冲突工作，或 patch 覆盖范围不足，则停止并报告差异。

### 4. 在获得授权后应用并验证 patch

仅在针对所声明基础的试运行或等效兼容性检查成功后应用 patch。重新检查所得 diff，并运行交接记录或清单中的聚焦验证。若应用或验证失败，保留证据并更新交接记录；不得强制应用、隐瞒部分应用或悄然重新生成 patch。

### 5. 继续或关闭任务

让 `handoff.md` 保持足以支持下一次有意设备切换的最新状态。工作被提交或放弃时，记录可观察结果，并依照状态仓库的保留规则移除或归档 patch 和清单。

## 完成标准

- 接收设备无需源设备对话即可识别预期项目和任务。
- 交接记录包含可验证的基线、证据、范围、下一步行动和未解决风险。
- 每个 patch 都有明确的基础提交、覆盖范围、应用方法和验证。
- 产品事实保留在产品仓库；临时状态保留在私有开发状态仓库。
