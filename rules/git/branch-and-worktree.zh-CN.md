# 分支与 Worktree 协调规则

> 英文语义源：[branch-and-worktree.md](branch-and-worktree.md)。

## 目的

使用分支和 Git worktree 隔离当前范围，同时避免形成彼此竞争的项目权威、隐藏状态系统或不必要的长期开发线。

## 隔离边界

- 除非目标项目明确规定另一种模式，否则只保留一个权威集成分支。
- 只有每条任务线归属明确、结果可独立验证，并且在文件、契约、接口、构建配置、迁移及其他可变状态上的重叠度较低时，才并行执行。
- 依赖性工作或集成敏感工作应串行执行。契约变更及依赖该契约的实现属于依赖链，不是相互独立的并行工作。
- 只为正在执行且已经授权的工作按需创建短期、按范围命名的分支。不得为预测、排队工作、贡献者、终端、工具或生命周期标签预建分支。
- 具体分支命名和并发限制由目标项目规定。

## 创建分支或 Worktree 前

确认仓库、权威集成分支、完整基础 commit、已授权范围、责任人、受影响契约与状态、依赖关系、集成顺序和所需验证。

创建或切换本地分支或 worktree 属于协调操作，不授权 commit、push、merge、删除分支、移除 worktree、重写历史或开始另一个排队任务。

## Worktree 隔离

- 每条真正并行的活动分支使用独立 worktree，一个 worktree 只承载一个活动范围。
- 不得在 worktree 之间隐式移动或共享未完成修改、生成输出、未跟踪文件、凭据或任务局部证据。
- 切换、集成或移除 worktree 前，检查 tracked、untracked、ignored 和 generated 状态。
- 机器特定的 worktree 路径属于本地协调状态，不得成为权威文档或交付状态。
- 只有存在真实跨设备或协作需要时才使用远程任务分支，并遵循适用的远程写入授权。

## 集成与清理

- 重新检查当前目标、任务分支、worktree、契约、实现、测试和验证证据。
- 显式解决不一致和冲突，再使用项目授权的方式按依赖顺序集成分支。
- 只在获批范围内重写尚未发布的历史；不得默认重写已共享历史。
- 当冲突解决或任务线交互改变证据边界时，重新执行与风险相称的验证。
- 集成后以集成目标为权威；任务分支属于执行历史，不是另一份当前状态。
- 只有确认分支或 worktree 不包含唯一 commit、未跟踪文件、生成证据、凭据、未解决冲突或必要交接后，才将其移除。清理仍是受授权约束的写操作。
- 仅为已识别恢复需要保留恢复引用，并在新状态稳定后复核。

## 项目特定规则

目标项目可以定义其集成分支、分支前缀、最大并行任务线、验证门禁、远程分支政策或更严格的清理要求。这些事实保留在产品仓库中，并以本规则作为可复用基线。
