# 架构决策记录

> 语义源：英文 [Architecture Decision Records](architecture-decision-records.md)。本文档为中文对应版本。

## 目的

定义架构决策记录（ADR）何时成为权威记录、实施前如何处理提案，以及已落地架构决定在日后被替换后如何保持可追踪。

## ADR 定位

ADR 记录一项已经实施、由适用作者或架构权威接受、完成 commit 并同步到指定共享 Git 历史的重要架构决定。它描述当前活跃或历史上曾经活跃的架构边界；它不是实施前提案、审批请求、实施计划，也不替代系统架构文档。

当决定具有持久的跨组件影响、回退成本较高、影响数据或兼容性、建立所有权或依赖边界，或者未来维护者需要理解系统为何采用该方向时，使用 ADR。决定不必完全不可逆。普通局部实现细节和低成本重构不需要 ADR。

## 实施前

在已授权任务或迭代、架构评审、技术评估或其他明确非权威工作材料中分析候选架构变更。在其中记录问题、选项、取舍、迁移计划、风险和作者方向。不得创建 Proposed ADR，也不得把已选择但尚未实施的方向表述为当前架构。

作者接受提案时，只授权其明确授予的范围。实施仍须遵守适用项目工作流和验证要求。

## 创建 Active ADR

只有在以下条件全部满足后才创建 ADR：

1. 重要技术方向已经实施。
2. 相关迁移与兼容行为已经验证或得到明确处置。
3. 作者或适用架构权威已经接受实施结果及其重要取舍。
4. 实现和对应文档已经 commit 并同步到指定共享 Git 历史。

此时创建的 ADR 状态为 `Active`。实际可行时，链接实现 commit、验证证据和此前的提案或评估。不得重构出当前证据无法支持的确定性。

## 状态枚举

每份 ADR 必须且只能使用以下状态值之一：

- `Active`：记录的决定管理当前已实现架构。
- `Inactive`：该决定在历史上曾管理已实现架构，但不再管理当前系统。

不得将 `Proposed`、`Accepted`、`Superseded`、`Deprecated` 或其他值作为 ADR 状态。提案状态属于实施前材料；接受是成为 `Active` 的前置条件，不是单独的 ADR 状态；被替换、被移除或不再适用应记录为 `Inactive` 的原因。

## 使 ADR 失效

当替代方案仍处于计划或实施阶段时，现有 ADR 保持 `Active`。只有替代或移除已经实施、接受、commit 并同步后，才将其改为 `Inactive`。

Inactive ADR 必须记录：

- 失效日期；
- 不再管理当前架构的原因；
- 存在替代 ADR 时记录其标识；
- 迁移、兼容性、数据或下游后果；
- 仍具有历史适用性的范围。

对于重要替代方向，创建新的 `Active` ADR 并双向链接。失效本身不授权回退、删除或迁移实现或数据。

## 记录完整性

- 使用目标仓库的追加式标识序列。不得重新编号、复用或改变 ADR 标识的用途。
- 将 Inactive ADR 保留为历史证据，不得重写成替代方案的描述。
- 可以修正事实或链接错误，但不得改变历史含义。
- 产品特定架构事实和 ADR 保存在产品仓库；本通用方法保存在 Toolkit。
