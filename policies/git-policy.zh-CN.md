# Git 政策

> 语义源：英文 [Git Policy](git-policy.md)。本文档为中文对应版本。

## 目的

在 Max 的各项目中维护可信、可读的 Git 历史，同时将仓库特定实现细节留给相关项目和专门的 Toolkit 技能。

## 提交政策

- 使用英文编写提交信息。
- 让每个提交表达一个连贯且可审查的变更。除非有明确理由，不要混合无关的实现、格式化、生成输出和政策变更。
- 仅描述暂存内容所支持的变更。不得在没有证据时声称测试通过、缺陷已修复或行为已改变。
- 遵循更具体且不与本政策冲突的明确项目约定。当需要 Conventional Commit 信息时，使用 Conventional Commit Generator 技能。

## 原子性和仓库一致性

- 让每次提交成为原子且可独立审查的变更：它应具有一个连贯目的，并可在不依赖无关暂存工作的前提下被理解、还原或拣选。
- 原子性不意味着单个文件或小 diff。将一个连贯变更所需的实现、测试和契约文档更新放入同一提交。
- 不要将未确认计划、临时任务状态、无关清理、生成输出或独立的行为变更与原本原子的变更混合。
- 提交后，其中的实现、测试和权威文档不得相互矛盾。该修订中的契约文档描述该修订已确认的状态，而不是待定或进行中的状态。

## 发布标签政策

- 使用带注释、不可变的发布标签。不得覆盖、移动、删除或强制推送现有发布标签。
- 使用项目记录的发布版本约定；若项目未约定，则使用带 `v` 前缀的语义化版本形式。
- 让发布标签、发布版本元数据和被标记的提交可追溯至相同的发布意图。
- 使用英文编写标签注释、发布说明和其他面向发布的文本。
- 在任何远程写入（包括推送发布标签）前获得明确确认。使用 Release Tag 技能获取验证和执行细节。

## 仓库完整性

- 不得提交机密、凭据、私钥、个人令牌或敏感的本地配置。
- 除非作者明确授权具体操作及其范围，否则不得重写共享历史或使用强制操作。
- 保留无关工作树变更。报告歧义，而不是默认丢弃、覆盖或暂存他人的工作。
- 在报告提交、标签、推送、合并、测试或发布操作已完成前，验证观察到的仓库状态。
